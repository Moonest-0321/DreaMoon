# 開發協作、UI 確認與聊天交接流程

> 更新日期：2026-09-01
>
> 目的：先釐清目前進度與需求、確認可能的 UI，再由使用者明確批准實作與測試；即使切換 Codex 聊天，也能接續同一個批准階段而不遺失關鍵決策。

## 1. 專案記憶分成三層

1. **長期事實**：規格、ADR、資料模型、程式、測試與 `docs/project-status.md`。
2. **目前功能工作單**：`docs/work-items/current.md`，保存需求、UI、驗收條件、批准狀態及實作／測試計畫。
3. **當前操作交接**：`docs/handoffs/current.md`，保存做到哪裡、工作樹邊界、測試結果與第一個下一步。

聊天用來討論與探索，但不是唯一紀錄。工作單回答「做什麼、已批准什麼」；交接回答「現在做到哪裡」。程式、測試與正式規格仍是最終事實來源。

## 2. 三個不可省略的批准點

| 關卡 | 使用者批准的內容 | 批准前 Codex 不得做的事 |
|---|---|---|
| R（Requirements） | 問題、範圍、非目標與驗收條件 | 進入 UI 定案或開始功能實作 |
| U（UI） | 入口、流程、畫面狀態與互動；無 UI 時標為 `not_applicable` | 將未確認介面直接寫成正式功能 |
| I（Implementation） | 技術拆解、風險及測試計畫 | 修改功能程式、資料模型或正式行為 |

切換聊天不會自動批准任何關卡。需求批准也不等於允許實作。

## 3. 完整工作流程

### 階段 0：說明目前進度

使用者提供能取得的資訊即可，不必先寫完整規格：

- 現在做到哪裡、目前看見什麼行為。
- 遇到的問題或希望改善的體驗。
- 最後希望使用者能完成什麼。
- 不能破壞的既有功能或資料。
- 截圖、草圖、參考產品或相關文件（若有）。

Codex 此時只做讀取、盤點、查證與提問，不修改功能程式。

### 階段 1：確認需求（R）

Codex 將討論整理到 `docs/work-items/current.md`，並回報：

- 對目前行為與問題的理解。
- 目標使用流程與主要情境。
- 必要範圍、可選項目、明確非目標。
- 可觀察或可測試的驗收條件。
- 限制、風險、待確認事項及暫時假設。

如有誤解，持續在此階段修改。使用者確認後說：

> `需求確認，進入 UI 提案。`

Codex 才把 R 記為 `approved`。

### 階段 2：提出並確認 UI（U）

只要涉及既有畫面或互動，Codex 在提出介面提案前必須實際檢視 app 的對應現況，至少涵蓋主要畫面與可取得的空白或已有資料狀態；程式碼閱讀不能取代此步驟。若環境無法檢視，需在提案中明確標示限制，並取得使用者畫面或方向後才設計。完成現況檢視後，Codex 應提供足以判斷的介面提案，視需要包含：

- 功能入口、資訊層級與操作順序。
- 一般、空白、編輯、錯誤、載入及刪除確認等狀態。
- 文字線框、圖片 mockup 或可互動原型。
- 一至三個合理方案、取捨及與現有 macOS／SwiftUI 介面的相容性。

這一階段可以反覆改 UI，但不實作正式功能。使用者確認後說：

> `UI 確認，請提出實作與測試計畫。`

Codex 才把 U 記為 `approved`。確定沒有 UI 影響時，工作單記為 `not_applicable`，並說明原因。

### 階段 3：確認實作與測試計畫（I）

Codex 根據已批准的需求與 UI，提出：

- 受影響的 model、store、service、view、文件與測試。
- schema、遷移、舊資料、刪除、匯出及跨模組相容性影響。
- 可逐一驗證的實作順序。
- 單元、整合、回歸及 UI smoke test 範圍。
- 風險、回復方式與本輪不處理項目。

使用者確認後說：

> `計畫確認，開始實作與測試。`

Codex 才把 I 記為 `approved` 並開始修改程式。

### 階段 4：分段實作

Codex 以小而可驗證的工作單元實作，每完成一段便更新工作單或交接檔。若實作中發現必須改變已批准的需求或 UI，應停止該分支並退回 R 或 U，而不是自行擴張範圍。

使用者直接要求的小型修正、純文件修改或明確指定的程式變更，可以略過不適用的關卡；Codex 必須在工作單說明略過原因。

### 階段 5：測試與修正迴圈

依風險執行適用驗證：

1. 編譯或靜態檢查。
2. 一般、空白、錯誤及重新開啟情境。
3. schema／遷移與舊資料相容性。
4. 跨模組回歸與既有測試。
5. `git diff`、`git diff --check` 與工作樹邊界檢查。
6. 環境允許時執行 UI smoke test。

失敗便修正並重跑受影響測試。沒有執行的項目只能標為「尚未驗證」，不可寫成通過。

### 階段 6：交付與使用者驗收

Codex 回報：

- 完成結果與實際操作方式。
- UI 是否符合已批准提案。
- 主要變更檔案及重要決策。
- 測試命令、結果、限制與未驗證範圍。

使用者可以回覆 `驗收通過`，或指出調整項目。若調整改變需求、UI 或技術計畫，分別退回 R、U 或 I。

### 階段 7：關閉與分流

驗收完成後，Codex 將長期資訊分流到規格、ADR、資料模型、測試文件與 `project-status.md`，並把目前工作單和交接檔標為 `closed`。不保存逐字聊天當作正式規格。

## 4. 安全切換聊天

最適合建立檢查點的時機：

- R、U 或 I 剛獲得批准後。
- 一個工作單元完成且相關測試已跑完後。
- 已確認阻礙及重現證據後。
- 對話明顯變長、準備暫停或切換聊天時。

在舊聊天輸入：

> `請依專案流程更新 work item 並建立交接檢查點，我要切換聊天。`

Codex 應同時更新：

- `docs/work-items/current.md`：需求、UI、驗收條件、R／U／I 與計畫。
- `docs/handoffs/current.md`：進度、工作樹、測試、阻礙與唯一下一步。

等 Codex 明確回覆檢查點完成後再換聊天。不要讓兩個聊天同時修改同一個工作樹。

## 5. 新聊天如何接續

在新聊天輸入：

> `依專案流程接續 current work item 與 handoff；先回報目前階段、已批准內容、工作樹邊界和下一步，不要重做已完成工作。`

新聊天依序讀取：

1. `AGENTS.md`
2. `docs/project-status.md`
3. `docs/work-items/current.md`
4. `docs/handoffs/current.md`
5. 兩份 current 文件指定的規格或技術文件
6. `git status`、相關 diff、程式與測試

接手者至少驗證一項關鍵事實，並先回報目前位於哪個階段。若 U 尚未批准，就只能繼續 UI 討論；若 I 尚未批准，就不能開始功能實作。

## 6. 資訊應放在哪裡

| 資訊 | 位置 |
|---|---|
| 目前需求、UI、驗收條件與批准狀態 | `docs/work-items/current.md` |
| 做到哪裡、測試結果、阻礙與下一步 | `docs/handoffs/current.md` |
| 專案整體現況與下一版本方向 | `docs/project-status.md` |
| 功能的長期正式行為 | `spec-*.md`／PRD |
| 架構決策及被否決方案 | `docs/decisions/` |
| schema、UUID、關係及刪除規則 | `data-model.md` |
| 遷移、備份與舊資料策略 | `backup-and-migration.md` |
| 測試方法與長期測試證據 | 測試報告與 `testing.md` |

## 7. 可直接複製的操作口令

- 開始討論：`我要規劃一項功能，先不要實作。我的目前進度是……；遇到的問題是……；希望最後可以……。請先盤點現況並整理需求。`
- 批准需求：`需求確認，進入 UI 提案。`
- 修改 UI：`UI 需要調整：……；先不要實作。`
- 批准 UI：`UI 確認，請提出實作與測試計畫。`
- 開始實作：`計畫確認，開始實作與測試；持續修正到通過。`
- 切換前：`請依專案流程更新 work item 並建立交接檢查點，我要切換聊天。`
- 新聊天：`依專案流程接續 current work item 與 handoff；先回報目前階段、已批准內容、工作樹邊界和下一步，不要重做已完成工作。`
- 完成驗收：`驗收通過，分流正式文件並關閉 work item 與 handoff。`
